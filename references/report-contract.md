# 固定汇报格式

默认管理摘要在约一分钟内可读。用户已有格式优先；不相关项写不适用或省略，不机械填长表。

## 阶段/交付汇报

**结论：**已完成 / 部分完成 / 受阻 / 失败。一句话解释对目标的影响。标注截至时间、环境和版本。

**任务目标：**要解决的问题与验收条件。

**实际结果：**可用成果及入口；还未完成的部分。分别列源码、部署和验收状态，不用模糊的“上线了”合并。

**验收证据：**关键验收项 → 通过/失败/受阻/未验证 → 对应证据。每份证据标环境、版本、采集时间与来源；详细记录可展开。

**业务价值：**已观察到的收益；估算及假设；未测量项。工作量与业务价值分开，不填虚构完成率。

**异常与处理：**问题、影响、已采取措施、下一步和责任归属。可独立处理的事项继续做。

**需要你决定：**无；或唯一必要问题、推荐方案、影响和期限。用户无需为代理的日常判断负责。

**下一步：**自动继续的授权工作及下一汇报节点。无法承诺时间时给触发条件。没有调度器时不能写“明天自动推送”。

## 紧急异常短报

结论与影响 → 已采取措施 → 当前阻塞 → 必要决策及建议 → 下一次更新节点。

先报告事实，避免等到固定汇总才暴露关键失败。渠道未获授权时，在当前对话汇报，不自行寻找收件人。

## 周期业绩

在上述格式前加统计窗口和范围；汇总按唯一任务/业务结果去重。至少明确：

- 约定目标、已验收成果、未完成/失败/暂缓项；不要只列成功项。
- 成功率的分子、分母和排除规则；范围改变时不直接比较。
- 已观察收益、估算收益、成本分别列示；AI/API 消耗、人工复核时间、维护成本有数据才写。
- 业务影响证据与执行量分开。把文档、子任务和代码提交累计成多项业绩会重复计功。

没有覆盖全周期的数据，只报告已观察窗口，不外推全年收益。

## 汇报触发

| 发生什么 | 处理 |
|---|---|
| 阶段完成、结果显著变化、恢复成功 | 主动汇报结果与证据 |
| 关键失败、到期风险、必须用户处理 | 在现有授权渠道及时汇报 |
| 普通进展 | 按已有节奏合并摘要 |
| 状态与证据无实质变化 | 留档或静默；按已约定的提醒/升级策略处理未解决关键事项 |

`quiet` 仅表示本次无需重复推送，未解决事项保留在任务台账；到达决策期限、升级时间或证据有效期需要调用方重新评估。结构化脚本不负责时间调度。
