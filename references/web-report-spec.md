# 网页结构规范

## 信息层次

首屏让用户能回答：交付了什么、能从哪里使用、哪些已经验证、还有哪些未完成，以及是否需要自己作决定。报告深度随需求规模变化，不要求填满无关栏目。

1. **交付概览**：项目名称、目标、环境与版本、报告日期、总体结论。用准确文字区分已完成、部分完成、受阻；不要用虚构完成率或绿色装饰淡化失败。
2. **产物与使用入口**：可点击地址或文件、进入路径、必要角色与前置条件。明确当前可用环境；源码、构建包、部署地址和报告分别标识。
3. **功能导航与明细**：桌面左侧固定功能目录、右侧功能内容；窄屏目录移到顶部。功能项标出状态，支持锚点直达。功能较少时可简化目录。
4. **验收与收益**：汇总关键业务场景是否通过、实际测得的相关收益及证据范围。细节在功能项中，不重复全文。
5. **未完成项与限制**：具体缺口、用户影响、下一步；仅在必须由用户处理时列出其所需动作。不要把代理仍可完成的工作交回用户。
6. **证据与技术附录**：用可展开区和链接放验证方法、完整测试结果、数据口径、代码位置、原始记录。结论与对应证据可互相定位。

## 新增功能块

推荐顺序：功能名称和状态 → 一句话说明价值 → 使用入口 → 实际截图 → 能完成的操作 → 验证结果和限制。

截图旁紧贴说明“画面证明了什么”。关键交互可用前后状态或短步骤组；静态截图不能证明发送、保存、权限、同步等后台行为，应补充实际验证结果。长截图选择能读清的尺寸，支持打开原图，避免把细字缩成缩略图后就算已展示。

## 替换功能块

推荐顺序：功能名称和一致性结论 → 同一场景的旧版/新版并排截图 → 行为与数据对照 → 差异影响 → 实测收益 → 证据。

每侧图片标注旧版/新版、环境、版本、采集日期、场景及必要角色。缺一侧时在原位置明确说明缺口，不使用看似真实的占位截图。

功能对照表按需采用：

| 检查项 | 旧版行为 | 新版行为 | 结论 | 依据或差异影响 |
|---|---|---|---|---|

不要仅因截图像就填“一致”；没有验证的行为填“未验证”。用户未要求改变的行为，差异不能自动写成优化。

## 视觉与交互

- 内容优先，安静的底色、清晰的正文、少量状态色。保留当前项目已有视觉风格，避免装饰性仪表盘和大量指标卡。
- 颜色搭配明确文字标签；使用语义化标题、图片说明、可键盘操作的链接与原生展开控件。
- 无 JavaScript 时主要内容和锚点仍可用。交互只服务于查找、比较、查看截图与证据。
- 图片保持比例；并排截图窄屏改为上下排列。用户应清楚每张图片属于哪个版本。
- 首屏不过度塞入测试日志；重要失败和限制不能藏进默认折叠的附录。
- 本地报告使用相对资源路径和内嵌或随目录提供的样式，不添加访问统计、第三方脚本或远程字体。

## 验收尺度

报告应既能让用户在一分钟内掌握结论，也能逐项核查细节。每项重要结论有证据，每项未验证内容有标签，每项产物有入口。报告质量以可理解、可核查、可使用衡量，不以页数、截图数或测试数衡量。

## 主动汇报与管理摘要

交付概览采用 [固定汇报格式](report-contract.md) 中与本任务有关的字段；无决策写“无”。将实际价值、估算和未测量分开。重大异常与必要决策放首屏，完整证据放附录。网页生成本身不表示已发送通知或已配置后续汇报。
